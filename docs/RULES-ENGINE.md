> **Coverage batch SUB4 (2026-07-15): banding (CR 702.22) — a faithful, documented SUBSET.** New `Keyword` member **banding**. Banding is notoriously complex; the tractable, decisive piece expressible in this combat model is **defensive damage-assignment control** (702.22h): in `dealCombatDamage`, when a blocked attacker is blocked by any creature with banding, the DEFENDING player assigns that attacker's combat damage — realised deterministically by funnelling ALL of it onto the (first) banding blocker (`bandSink`), sparing the rest of the block and **negating trample** (excess is assigned to the band member, not trampled through). **OUT OF SCOPE (documented):** attacking-as-a-band grouping and OFFENSIVE banding (702.22i, the attacker assigning the blockers' damage) — both need multi-creature bands / an interactive damage-assignment order this auto-assigning model doesn't have. Cards: **Benalish Hero** {W} 1/1 banding, **Mesa Pegasus** {1}{W} 1/1 flying banding. No hidden-info surface / no new action → no fuzzer change. `tests/unit/rules-staples-sub4.spec.ts` (2 tests: a banding blocker absorbs the whole attack so a 2/2 co-blocker survives untouched; a lone banding blocker negates a 6/6 trampler so the defender takes 0). **Review:** inline (workflow reviews still blocked by the org spend limit) — verified the `continue` skips only the defaulted per-blocker + trample assignment for that attacker, deathtouch/co-blocker strike-back are unaffected, and only DEFENSIVE (blocker-side) banding triggers. Full suite (521) + build green.

> **Coverage batch SUB3 (2026-07-15): phasing (CR 702.26 / 502.1).** New `Keyword` member **phasing** + `GameObject.phasedOut` / `phasedOutBy` (indirect). At the start of the active player's untap step (before untap-all), `runPhasing`: their phased-OUT permanents phase in, and their permanents with phasing (phased in) phase out — simultaneously, alternating each of that player's turns. A phased-out permanent stays in the battlefield zone but is **treated as though it doesn't exist**: excluded from `battlefieldCreatures` / `isCreatureOnBattlefield` (⇒ combat, SBA, sweepers), from `isPermanentOnBattlefield` (⇒ targeting), from the untap loop, and its static anthems/lords/keyword-grants are off (`characteristics.ts` skips phased-out sources); it also can't attack/block/`r.tapMana`/`r.activate`/be equipped. Phasing never counts as entering/leaving (no ETB/LTB, no summoning-sickness reset — continuous control). Attachments phase out and back in **with** their host, tracked via `phasedOutBy` (CR 702.26e). Phased-out permanents are fully public — the redactor sends a `phasedOut` flag (no hidden-info surface / no new action → no fuzzer change); the client greys them + shows a "Phased" badge. Cards: **Teferi's Honor Guard** {3}{W} 2/4 phasing, **Rainbow Efreet** {4}{U}{U} 4/4 flying phasing. `tests/unit/rules-staples-sub3.spec.ts` (2 tests: out→untargetable/unswept→back-in-untapped-non-sick; Equipment indirect-phasing round-trip stays attached). **Review:** inline (workflow reviews still blocked by the org spend limit) — found + fixed a real gap: `r.equip` didn't reject a phased-out Equipment or a phased-out target creature (added both guards). Full suite (519) + build green.

> **Coverage batch CASCADE (2026-07-12) — LEAK-CRITICAL: cascade (CR 702.85).** New `CardDefinition.cascade`, `StackItem.cascade {mv}`, a `pending: 'cascade'` decision + `pendingCascade {player, hitId, exiledIds}`, and `r.cascade {cast, targets, mode}`. Casting a cascade spell hooks in `r.cast` (`queueCascade`) to put a cascade trigger on the stack ABOVE it (resolves first). `resolveCascade` moves cards from the top of the library to **exile face-up (public)** until a nonland with `manaValue < the cascade spell's` (or the library empties); a hit opens the may-cast-free decision, else it bottoms everything. `r.cascade`: **cast** (`freeCastFromExile` — validate targets atomically, then put the hit on the stack for {0}, X=0; ward still applies) or **decline**; then the passed-over cards (plus the hit if declined) go to the **bottom in a random order** (`shuffleInPlace`) and the **whole library is re-minted** (`remintLibrary`). **Leak-critical:** the exiled cards are public in exile, so the re-mint on return to the hidden library kills any tracking (invariant #3); library order is never serialized (#2). `repairControlFlow` bottoms everything if the decider leaves. Client: a **banner** (non-blocking, so the battlefield stays clickable) — click a legal target to free-cast, with **Decline** always present (so an unsupported hit can only *limit*, never wedge). Cards: **Shardless Agent** {1}{G}{U} 2/2 (MV 3), **Bloodbraid Elf** {2}{R}{G} 3/2 haste (MV 4). Cascade on the free-cast card is intentionally NOT re-triggered (documented simplification). `tests/unit/rules-staples-cascade.spec.ts` (7 tests) + a deterministic history-aware exile→bottom re-mint test in `rules-leak.spec.ts` + a `cascade` fuzzer branch (declines → exercises the re-mint) with Bloodbraid Elf in FUZZ_DECK. **Adversarial-review workflow (4 lenses → verify) — the leak-critical, no-wedge, and anti-cheat lenses were all clean; found 2 confirmed CLIENT free-cast UX gaps (fixed):** (1) *medium* — a **modal** hit reported no target, so the banner offered a target-less "Cast free" button that always errored (server picks mode 0, needs a target); (2) *low* — hits needing a `spell`/`graveyardCard`/multi-target couldn't be delivered by the client (Decline only). Both are UX, not leaks/wedges (Decline always works; target validation is atomic). Fixed by having `redact` report accurate client-castability signals — `cascadeCanFreeCast` (non-modal, zero targets) + a single client-deliverable `cascadeTargetKind` (null for modal/multi/spell/graveyardCard) — so the banner only offers a working action, else Decline-only; the engine already accepts a full `r.cascade` with targets+mode, so complex free-casts are a documented client limitation, not an engine gap. Regression tests assert the signals for a single-target (Shock), no-target (Night's Whisper), and modal (Abrade) hit.

> **Coverage batch WARD (2026-07-12): ward (CR 702.21) — the "pay-or-counter" mechanic.** New `CardDefinition.ward` (mana cost), `StackItem.ward {triggeringId, cost, payer}`, a new `pending: 'ward'` decision + `pendingWard`, and the `r.ward {pay}` action. When a spell or ability an OPPONENT controls targets a permanent with ward, `queueWardTriggers` pushes a ward trigger ABOVE the triggering item for each targeted opponent-controlled warded permanent; since `resolveTop` pops-then-resolves, the ward trigger resolves first (via the `resolveAbility` ward branch) and opens a pay-or-counter decision for the triggering item's controller — who got a normal priority window BEFORE it to float the ward mana. `r.ward`: pay from the pool (atomic; unaffordable → counter) or decline → `counterStackItem` (a spell → its owner's graveyard, an ability → spliced off). Safe no-op if the triggering item already left the stack; `repairControlFlow` counters it if the payer leaves mid-ward. `redact` exposes `needsWard`/`wardCost`/`wardAffordable` to the payer only; the client shows a Pay/Decline modal. Cards: **Tomakul Honor Guard** {1}{G} 3/1 Ward {2}, **Waterfall Aerialist** {3}{U} 3/1 Flying Ward {2} (mana ward only — ward—pay-life / ward—discard deferred; granted ward deferred). Leak-safe (pending/stack/battlefield ids public; prompt actor-only). `tests/unit/rules-staples-ward.spec.ts` (7 tests) + a deterministic ward leak-coverage test in `rules-leak.spec.ts` + a `ward` pending branch and Tomakul Honor Guard in the CI fuzz deck. **Adversarial-review workflow (4 lenses → verify) found 1 confirmed HIGH defect (fixed red→green):** targeted **triggered abilities** bypassed ward — `queueWardTriggers` was wired only to `r.cast`/`r.activate`, but a targeted trigger reaches the stack via `r.chooseTargets` (and a targeted loyalty ability via `r.loyalty`), which skipped ward, so an ETB removal (Ravenous Chupacabra, Flametongue Kavu) targeting a warded creature silently skipped the pay-or-counter (CR 702.21a is "spell OR ability"). Fixed by calling `queueWardTriggers` from `r.chooseTargets` and `r.loyalty` too, with red→green regression tests (Chupacabra's ETB now fires ward: paying lets it resolve, declining counters it).

## Context & honest scope

Goal: an **Arena-like enforced mode** — the app knows the rules, only lets you take legal actions, resolves the stack, applies effects. This is the opposite of the current manual table (invariant #6: "no rules enforcement").

**This is a multi-year, perpetual program, not a task.** "All ~28,000 cards with every interaction" is XMage-scale (≈20 years, many contributors, hundreds of cards hand-coded per set, *forever*). No one ships it in one pass. What we build is:

1. a **correct rules-engine core** (the hard, finite part), and
2. a **card-scripting framework** so cards are mostly declarative data, plus
3. a **card library that grows every milestone, indefinitely.**

### Decisions (confirmed with the user)

- **Coexist, don't replace.** Enforced mode is a new per-lobby option alongside the manual table. Implemented cards play with full rules; the manual table remains the fallback for everything not yet coded — preserving "works with any card day one." Invariant #6 is relaxed *only for enforced games*; manual games keep it.
- **Bring the engine up in 1v1 / 20 life first.** Multiplayer priority, politics, Commander (40 life, command zone, tax, commander damage) multiply the hardest engine problems — defer them to M-R4. Duels prove the spine fastest.
- **Prove it on a tiny curated card set** (~12 → ~50 cards), not a precon or a full set. Each later milestone grows coverage.

## Reuse (build on the existing plumbing, don't duplicate)

The enforced engine reuses, unchanged where possible:
- **ws transport & room registry** — `server/game/room.ts` (single-flight rehydrate, snapshot cadence, rate limiting, presence). Add a `mode` branch.
- **Redaction discipline** — `server/game/visibility.ts` (`redactStateFor`, `visibleTo`, id re-minting on hidden-zone entry). The rules state redacts the same way; library order stays secret, hands hidden. This is non-negotiable and reused wholesale.
- **Persistence** — full-state snapshot to `Game.snapshot` jsonb (mode-tagged); no replay needed.
- **Protocol shape** — `shared/schemas/messages.ts` discriminated-union pattern; enforced mode adds its own message variants.
- **Client renderer** — `app/components/board/*` renders zones/cards/stack already; enforced mode *adds* a priority bar, legal-action highlighting, targeting/choice prompts, and "yield/auto-pass" — it does not rebuild the board.
- **Card catalog** — `Card` (oracleText, typeLine, manaCost, power/toughness, keywords, colorIdentity, faces) seeds card definitions; hand-authored definitions override/augment it.

## Architecture

Server-authoritative, **event-driven**, deterministic given the shuffle RNG (reuses `server/game/rng.ts`). New code under `server/rules/`; shared types under `shared/rules/`.

```
server/rules/
  state.ts        # RulesGameState, GameObject (characteristics + status), zones, mana pool
  engine.ts       # the loop: advance steps, grant priority (APNAP), resolve stack, run SBA
  turn.ts         # phase/step machine (untap→upkeep→draw→main1→combat…→main2→end→cleanup)
  priority.ts     # priority passing; "all passed" → step advance or top-of-stack resolves
  stack.ts        # cast spell / activate ability → put on stack; resolve LIFO
  cost.ts         # cost determination + payment (reuses shared/utils/manaCost.ts) ; mana abilities
  targeting.ts    # legal-target computation + validation ("as you cast/activate")
  sba.ts          # state-based actions (lethal damage, 0 toughness, 0 life, later: +1/-1 annihilation, legend rule)
  combat.ts       # declare attackers/blockers, ordering, first-strike/normal damage steps
  events.ts       # GameEvent taxonomy + observe hooks (triggered abilities, later: replacement/prevention)
  layers.ts       # [M-R1] continuous-effects layer system (rule 613) — the hardest subsystem
  actions.ts      # player action handlers → engine calls (cast, activate, pass, declare, choose targets/modes/X)
  legal.ts        # enumerate legal actions for the player with priority (drives client affordances + validation)
  cards/
    dsl.ts        # CardDefinition + Ability + Effect primitives (the scripting framework)
    effects.ts    # composable effect primitives: dealDamage, draw, destroy, gainLife, addCounters, createToken, pumpEOT…
    keywords.ts   # [M-R1] flying, trample, deathtouch, lifelink, vigilance, haste, first strike, double strike, menace, reach, defender
    registry.ts   # normalized-name → CardDefinition
    sets/starter.ts  # the curated card definitions
shared/rules/
  state.ts        # RulesClientState (redacted), extra fields: priorityPlayer, legalActions, pending choices, stack view
  messages.ts     # enforced-mode client messages (zod)
```

### Core model

- **GameObject**: id, ownerId, controllerId, zone, characteristics (name, manaCost, colors, types/subtypes/supertypes, basePower/baseToughness, abilities), plus status (tapped, flipped, faceDown, phasedOut), counters, damageMarked, attachments, summoningSick. Continuous effects (M-R1) are applied over base characteristics via the layer system to yield *current* characteristics.
- **Card DSL** (`cards/dsl.ts`) — a card is data:
  ```ts
  interface CardDefinition {
    name: string
    types: CardType[]; subtypes?: string[]; supertypes?: string[]
    manaCost?: string; colors?: ManaColor[]
    power?: number; toughness?: number
    abilities?: Ability[]
  }
  type Ability =
    | { kind: 'spell'; targets?: TargetSpec[]; effect: Effect }          // instant/sorcery
    | { kind: 'activated'; cost: Cost; isMana?: boolean; targets?: TargetSpec[]; effect: Effect }
    | { kind: 'triggered'; when: EventFilter; effect: Effect }           // [M-R2]
    | { kind: 'static'; mod: StaticMod }                                 // [M-R1]
    | { kind: 'keyword'; keyword: Keyword }                              // [M-R1]
  type Effect = (ctx: EffectContext) => void   // mutates game via engine primitives only
  ```
  Coverage grows by adding **effect primitives** (`effects.ts`) and **card definitions** (`sets/*`). Most cards become a few lines of data; genuinely unique cards get bespoke `Effect` code.

### Hidden information

The rules state redacts through the same principles as the manual engine (own hand visible, opponent hand count-only, library order never serialized, face-down identity hidden). The rules-leak fuzzer (CI-blocking) fuzzes 2/3/4-player games — now **history-aware** (an id currently in a hidden zone must never have been serialized to that viewer before) and exercising the manual overrides, so a public→hidden move that failed to re-mint would fail it. **This constraint is preserved, not relaxed** — the assisted-table manual moves (`r.mMove`) re-mint an object's id on public→hidden entry, exactly like the manual engine.

## Coexistence wiring

- `Lobby.mode: MANUAL | ENFORCED` (Prisma migration; default MANUAL). Start builds either the manual `ServerGameState` or a `RulesGameState`; both snapshot into `Game.snapshot` (tagged) and run in the same room registry.
- Enforced start validates only that each deck has **exactly one commander that is a legendary creature** (registry def OR catalog type line). Unimplemented cards **do not block** — the assisted table gives them a catalog-derived body (`server/rules/cards/fallback.ts`, registered via `registerFallback` in lifecycle before `buildRulesGame`; idempotent, never overwrites a real def).
- ws handler routes by the room's mode to the manual reducer or the rules engine. The rules engine accepts the manual-override messages (`r.m*`) any time the game is active; a `repairControlFlow` safety net runs after every action so a player who self-eliminates (e.g. `r.mLife` to 0) while owing a pending decision or holding priority can't wedge a 3–4 player game.
- **Known limitation:** `r.mToken` interns each distinct token spec in a process-global registry that is never freed; a client spamming unique specs grows memory over the process lifetime. Acceptable for a self-hosted table; revisit (instance-level token defs) if it matters.

## Risks / non-goals for M-R0

- Riskiest subsystem overall is the **layer system (M-R1)** and **replacement effects (M-R3)** — deferred deliberately; M-R0 uses only vanilla creatures + direct-damage so it needs neither.
- No triggered abilities, no continuous effects, no keywords in M-R0 (M-R1).
- Not multiplayer/Commander yet (M-R4).
- Card coverage is perpetual; "Arena parity" is the horizon, not a milestone.
