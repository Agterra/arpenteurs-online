# Stack research report — Nuxt 4 Commander table (verified July 2026)

## 1. Nuxt 4

- **Current stable: Nuxt 4.4.8** (June 2026). Nuxt 4 GA'd July 2025; the 4.4 minor (March 2026) brought Vue Router v5, `useFetch` factories, typed layout props, better import tracing. Nuxt 3 maintenance ends **end of July 2026**. Sources: [installation docs (shows v4.4.8)](https://nuxt.com/docs/4.x/getting-started/installation), [GitHub releases](https://github.com/nuxt/nuxt/releases) (parallel 4.4.x / 3.21.x trains, latest 4.4.8 + 3.21.8), [eosl.date](https://eosl.date/eol/product/nuxt/), [changelog](https://nuxt.com/changelog).
- **Scaffolding**: `pnpm create nuxt@latest <project-name>` (npm: `npm create nuxt@latest`). **Node requirement: 22.x or newer** — your Node 24 is fine. Dev server: `pnpm dev -o`. Source: [installation docs](https://nuxt.com/docs/4.x/getting-started/installation).
- **Directory layout** ([app/ docs](https://nuxt.com/docs/4.x/guide/directory-structure/app)): client code lives under **`app/`** (`app.vue`, `error.vue`, `app.config.ts`, `assets/`, `components/`, `composables/`, `layouts/`, `middleware/`, `pages/`, `plugins/`, `utils/`). **`server/`, `shared/`, `public/`, `nuxt.config.ts`, `prisma/` stay at project root.**
- **`shared/` directory** ([docs](https://nuxt.com/docs/4.x/directory-structure/shared)): code usable by both Vue app and Nitro. **Only `shared/utils/` and `shared/types/` are auto-imported, and only their top level** — nested subfolders and top-level `shared/*.ts` files are NOT auto-imported; use the auto-configured **`#shared` alias** for those (`import { GameMsg } from '#shared/messages'`). Constraint: shared code must not import Vue or Nitro code. Perfect home for your zod message schemas + zone/game TypeScript types.
- **Key `nuxt.config.ts` for this project**:
```ts
import tailwindcss from '@tailwindcss/vite'
export default defineNuxtConfig({
  compatibilityDate: '2026-07-01',
  modules: ['@pinia/nuxt', '@nuxt/ui', '@nuxt/test-utils/module'],
  css: ['~/assets/css/main.css'],
  vite: { plugins: [tailwindcss()] },   // omit if @nuxt/ui already wires Tailwind v4 (it bundles it)
  nitro: {
    experimental: { websocket: true },  // Nitro v2 syntax used by Nuxt 4
  },
  runtimeConfig: { databaseUrl: '' },   // override via NUXT_DATABASE_URL
})
```

## 2. WebSockets in Nuxt 4 / Nitro

- **Enable flag (Nuxt 4 / Nitro 2.x)**: `nitro: { experimental: { websocket: true } }` in `nuxt.config.ts` — confirmed by [NuxtHub realtime guide](https://hub.nuxt.com/docs/guides/realtime) and [socket.io's Nuxt guide](https://socket.io/how-to/use-with-nuxt). (The `features: { websocket: true }` syntax on [nitro.build/docs/websocket](https://nitro.build/docs/websocket) is **Nitro v3** config for standalone Nitro/Nuxt 5 — don't copy it into a Nuxt 4 app.) Still flagged *experimental* in mid-2026.
- **Handler location**: normal Nitro file-based routing — put it in **`server/routes/`**, e.g. `server/routes/ws/game.ts` → `wss://host/ws/game`. (`server/api/` also works but routes is the documented convention; NuxtHub uses `server/routes/ws/visitors.ts`.)
- **API** (`defineWebSocketHandler`, powered by [crossws](https://crossws.h3.dev)): hooks `upgrade(req)`, `open(peer)`, `message(peer, message)`, `close(peer, details)`, `error(peer, error)` (+ `ping`/`pong`/`drain`). Message accessors: `message.text()`, `message.json<T>()`, `message.uint8Array()`. Sources: [Nitro websocket docs](https://nitro.build/docs/websocket), [crossws hooks](https://crossws.h3.dev/guide/hooks), [crossws peer](https://crossws.h3.dev/guide/peer).
- **Peer API**: `peer.id` (uuid v4), `peer.send(data)` (string/object/binary), `peer.subscribe(topic)` / `peer.unsubscribe(topic)` / **`peer.publish(topic, data)` — the publishing peer is EXCLUDED from its own broadcast** (so echo state back with an explicit `peer.send`), `peer.peers` (peers in namespace), `peer.topics`, `peer.context`, `peer.close(code?, reason?)`, `peer.terminate()`, `peer.request` (upgrade Request — headers/cookies), `peer.remoteAddress`. Namespaces default to the request pathname (one handler file = one namespace); overridable from `upgrade`.
- **Auth on upgrade**: `upgrade(req)` receives a web-Request-like object: `req.headers.get('cookie')`, `req.url`; **reject by returning a `Response` (e.g. 401)**; accept by returning `{ headers, context }`. **Known Nuxt bug: context returned from `upgrade` does NOT arrive in `peer.context` in `open`** — [nuxt#33829](https://github.com/nuxt/nuxt/issues/33829) (repro on Nuxt 4.2.1 / Nitro 2.12.9, closed "not planned"). Practical pattern: validate the cookie token in `upgrade` (reject bad ones), then **re-read it in `open` via `peer.request.headers.get('cookie')`** and parse it yourself (h3's `getCookie(event)` isn't available here — parse the header with the `cookie` npm package or a 3-line splitter). Community confirms this is the current workaround ([Nitro cookie discussion](https://www.answeroverflow.com/m/1371089006917320885)).
- **Dev-mode pitfall**: any edit to a `server/` file triggers a full Nitro dev-server reload — **all module-level in-memory state (your room Maps) is wiped and every socket drops**. There's no HMR state preservation for Nitro; the dev proxy's ws support itself was reworked in the new CLI ([nuxt/cli#108](https://github.com/nuxt/cli/issues/108), [nitro ws tracker #2171](https://github.com/nitrojs/nitro/issues/2171)). Your planned architecture already absorbs this: DB snapshots + rehydrate-on-boot + client auto-reconnect makes dev reloads a non-event. Build that rehydration path early — it doubles as your "survive server restart" feature.
- **Production (node-server preset)**: fully supported — Nitro lists **Node.js**, Deno, Bun, Cloudflare as supported ws presets ([NuxtHub guide](https://hub.nuxt.com/docs/guides/realtime)); on Node it runs on the battle-tested `ws` package via the crossws node adapter; pub/sub is in-process (fine for single-node self-hosted; no Redis needed).
- **VERDICT**: **Use Nitro native websockets.** For a self-hosted, single-node, 4-players-per-room game it's production-ready in mid-2026: stable on the node preset, used in production by NuxtHub, zero extra server infra, handlers colocated with your Nitro API. The "experimental" flag mostly signals API surface may still move (as #33829 shows) — pin your Nuxt version and keep auth in `open` via `peer.request`. socket.io remains the fallback if you later need auto-fallback transports, acks, or multi-node scaling — its [Nuxt integration](https://socket.io/how-to/use-with-nuxt) itself now rides on the same experimental Nitro ws flag, so it no longer buys you stability, only features you don't need. Reconnect/heartbeat you handle client-side (see §5).

## 3. Prisma (mid-2026)

- **Current major: Prisma 7** (7.0.0 released **Nov 19, 2025**; latest ≈ **7.8.0**, with 6.19.x maintenance backports). Rust-free, **ESM-native client**: ~90% smaller bundles, up to 3x faster queries. Sources: [announcement](https://www.prisma.io/blog/announcing-prisma-orm-7-0-0), [releases](https://github.com/prisma/prisma/releases), [v7 upgrade guide](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7).
- **Breaking vs v6**: generator provider is now **`prisma-client`** (old `prisma-client-js` deprecated, will be removed); **`output` path is required** — client is no longer generated into `node_modules`; driver adapters are the norm (`@prisma/adapter-pg` + `pg` for Postgres).
- **Nuxt integration: do NOT use `@prisma/nuxt`** — the module is **deprecated / unmaintained**, new projects explicitly told not to use it ([github.com/prisma/nuxt-prisma](https://github.com/prisma/nuxt-prisma), [nuxt.com/modules/prisma](https://nuxt.com/modules/prisma)). **Recommended: manual singleton in `server/utils/db.ts`** per the [official Prisma Nuxt guide](https://www.prisma.io/docs/guides/frameworks/nuxt): `new PrismaClient({ adapter: new PrismaPg({ connectionString }) })`, stashed on `globalThis` outside production to survive dev hot reloads; auto-imported into all API routes/ws handlers via Nuxt's `server/utils` scanning.
- **Schema/generate workflow**: `prisma init` → `prisma/schema.prisma` with `generator client { provider = "prisma-client", output = "../server/generated/prisma" }` (any path inside the server build works; guide uses `./generated`); deps `@prisma/client @prisma/adapter-pg pg`, dev-deps `prisma @types/pg`; `prisma migrate dev` for migrations; add **`"postinstall": "prisma generate"`** to package.json so the client exists at build time. Import the client **from the generated path**, not `@prisma/client`.
- **ESM/Nitro gotchas**: the historical Nuxt blocker — `File URL path must be absolute` from `import.meta.url === 'file:///_entry.js'` when Nitro bundles the engine-based client ([prisma#26857](https://github.com/prisma/prisma/issues/26857), filed vs 6.6.0) — is largely defused by v7's engine-less client (no native `.node` engine file to resolve). Remaining v7 wart: generated ESM code uses `.js` specifiers for `.ts` files, which breaks *Webpack* bundlers ([prisma#28627](https://github.com/prisma/prisma/issues/28627)); Nitro's Rollup/esbuild pipeline handles it, but if you hit resolution errors the escape hatch is adding the generated dir to `nitro.externals`/`moduleSideEffects` or generating with `importFileExtension` tweaked. Test `pnpm build && node .output/server/index.mjs` early.
- **Local Postgres (docker compose)**: current Postgres is **18.x (18.4)**; Prisma 7.2+ verified working with PG 18 though official support listing lagged ([prisma discussion #28937](https://github.com/prisma/prisma/discussions/28937)); **postgres:17-alpine is the zero-surprise pick**, 18 fine if you want it (note: in the v18 image `PGDATA` moved to `/var/lib/postgresql/18/docker` — [docker hub](https://hub.docker.com/_/postgres)). Standard compose: `image: postgres:17-alpine`, `POSTGRES_USER/PASSWORD/DB` env, `ports: ["5432:5432"]`, named volume on the data dir, `healthcheck: pg_isready`.

## 5. SSR pages + client WebSockets gotchas

- **Never open a socket during SSR**: `WebSocket` doesn't exist server-side. Open in `onMounted()` or guard with `import.meta.client`. The Nuxt-blessed pattern ([NuxtHub guide](https://hub.nuxt.com/docs/guides/realtime)) is VueUse `useWebSocket(url, { immediate: false, ... })` + `onMounted(() => open())`.
- **Hydration**: don't render socket-derived state in SSR output (it's empty server-side → mismatch). Render the static shell + SSR-fetched data (lobby info via `useFetch`), then patch live state after mount; wrap purely-live widgets in `<ClientOnly>`. For the game board this is natural: SSR renders the page frame, the ws `sync` message paints the board.
- **Cookie identity**: set the long-lived token with `useCookie('player_token', { maxAge: 60*60*24*365, sameSite: 'lax', httpOnly: false-ish via server route })` — better: mint it in a server route with `setCookie(event, ..., { httpOnly: true })`. Browsers **automatically include cookies on a same-origin ws upgrade** (it's a normal GET with `Upgrade: websocket`), so the exact same cookie arrives in the upgrade request — read `req.headers.get('cookie')` in `upgrade` / `peer.request.headers.get('cookie')` in `open` and parse manually (no `getCookie(event)` there; use the `cookie` package). No token-in-query-string needed since front and ws share the origin. Caveat: due to [nuxt#33829](https://github.com/nuxt/nuxt/issues/33829), parse in `open`, don't rely on `upgrade`-returned context.
- **Auto-reconnect**: native `WebSocket` has none. Use VueUse `useWebSocket` — `autoReconnect: { retries: -1, delay: ... }` (backoff via delay function), `heartbeat: { message: 'ping', pongTimeout }` keeps proxies from idling the connection ([VueUse docs](https://vueuse.org/core/usewebsocket/)). On reconnect the server must resend a full state snapshot for that peer (your reconnect-mid-game requirement) — design a `hello {token} → sync {fullRedactedState}` handshake so reconnect and dev-reload are the same code path. A ~50-line hand-rolled wrapper is also fine, but VueUse gives reconnect + heartbeat + `status` ref for free and you'll likely pull `@vueuse/core` anyway.
- **Build url client-side**: `const url = \`${location.protocol === 'https:' ? 'wss' : 'ws'}://${location.host}/ws/game\`` — computed at mount time only (SSR-safe since it runs client-side).
