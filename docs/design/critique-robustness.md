## [blocker] Stable per-game CardIds enable cross-zone identity tracking of hidden cards
The redaction section claims ids are 'only ever serialized once identity is visible', but CardId is minted once per instance and never changes. Any card whose id became public (played, discarded to graveyard, revealed via hand.reveal / deck.revealTop / revealedTo) and then enters a hidden zone (bounced to hand, tucked to library, shuffled in via 'shuffle graveyard into library' effects) keeps its known id. Opponents can then map id->identity the moment that id resurfaces in any event or snapshot: a 'card.moved hand->library top' event carrying cardId tells everyone exactly which card is on top of the library (worse than paper); a formerly-public card drawn and played is trackable across the shuffle, defeating the shuffle itself. The doc never specifies whether hidden-destination card.moved events include cardId, and the visibleTo() predicate as described is point-in-time, not history-aware. Fix: (a) mint a fresh CardId whenever a card enters a hidden zone (hand from non-hand, library, face-down exile) and on every shuffle re-key all library ids; (b) strip cardId from every event whose card is not visible to the recipient at event time; (c) extend the CI leak property test to assert that no id present in a hidden zone was ever previously serialized to that viewer (history-aware check, not just point-in-time grep).

## [blocker] The two design docs specify two incompatible systems — pick one before any code is written
The 'data' and 'engine' docs contradict each other on core mechanisms: (1) persistence — data doc: one transaction per action writing event + FULL snapshot with snapshotSeq optimistic guard, 'events never replayed'; engine doc: write-behind queue, snapshot every 25 actions/15s, recovery = deterministic replay of the event tail through the reducer with recorded fx. These have different crash semantics, different GameEvent schemas (publicLog/payload vs action/fx), and different hot-path latency (the data model forces an awaited DB round-trip per action, contradicting the engine's 'zero awaits before broadcast' serialization argument). (2) Auth/schema — data doc stores sha256(token) in User.tokenHash; engine sketch has Player(token, name) storing the RAW token (a DB leak = full session theft) and 'bcrypt-hashed password' vs the data doc's scrypt. (3) API surface — REST lobby endpoints + WS /api/games/:id/ws + bootstrap endpoint (data) vs lobby.ready/lobby.start over WS at /ws/game?g= with no bootstrap (engine). (4) Prisma — data schema uses provider prisma-client-js + previewFeatures, engine research mandates Prisma 7 provider 'prisma-client' with required output and @prisma/adapter-pg; the data schema as written won't work on Prisma 7. Fix: adopt the engine doc's persistence/replay + scrypt + hashed token, port the data doc's Prisma schema to Prisma 7 syntax, and reconcile the endpoint list into one table; also note the data model's per-action full-snapshot write is ~150 KB x every action (a 3-hour game with drag events = hundreds of MB of WAL/TOAST churn), so the engine cadence should win.

## [blocker] card.move by id out of the library = silent tutor that bypasses search/shuffle
card.move row 26 explicitly allows moving 'from a peek' and generally between any zones, and the authorization matrix only checks controller/owner — nothing restricts the SOURCE zone. A player who knows the id of a card in their own library (trivially obtained today because ids are stable across shuffles — see the id-tracking finding — or via an open peek) can send card.move {cardId, to: hand} and extract an exact card with a log line no scarier than 'moved a card from library to hand', bypassing deck.search's forced shuffle and the 'searched their library' log. Fix: the reducer must reject any card.move whose current zone is a library unless the card is listed in the actor's active Peek (and search-mode extraction should still set the pending-forced-shuffle flag); peek.resolve must validate toTop ∪ toBottom ∪ moves ⊆ peek.cardIds and reject duplicates/unknown ids, otherwise the same tutor exists through a forged peek.resolve.

## [important] Open peek vs concurrent library mutation is unspecified (stale peek corruption)
A player can open a scry/look peek and then, while it is open, send deck.draw, deck.shuffle, deck.mulligan, or card.move into their library — none are blocked. The Peek.cardIds then reference cards that are no longer the top N (or are now in hand), and a later peek.resolve will reorder/move the wrong cards or violate the zone/array invariant (a card in hand also listed in toTop). Fix: while state.peeks[player] exists, the reducer rejects all library-touching actions for that player's library (draw, shuffle, mulligan, moves into/out of it) with a PEEK_OPEN error, or auto-cancels the peek (with search's forced shuffle preserved) before applying. Also specify what happens to an open peek when the game ends or the player disconnects (currently it survives in state forever).

## [important] Events for hidden->public transitions don't carry the card object for opponents (guaranteed desync)
peek.resolved sends opponents only a numeric summary, but peek.resolve's moves[] can place a searched card directly onto the battlefield or into the graveyard — public zones. With summary-only payloads, opponents' stores never receive the CardInstance that just materialized in a public zone; their state silently diverges until a manual resync. Same class of bug: deck.mulliganed (hand contents visibly change), and card.move of a face-down battlefield card into the graveyard/exile face-up (the redaction table has no row for 'face-down card in a public zone' — is a morph dying revealed or not? paper says yes). Fix: specify that every redacted event enumerates, per recipient, the full redacted card objects for all cards whose visibility CHANGED as a result of the action (the visibleTo(before) != visibleTo(after) delta), and add rows to the redaction table for face-down cards in graveyard/stack/exile transitions. The CI property test should assert event-applied client state deep-equals redactStateFor(viewer, newState) after every fuzzed action — that catches this whole class.

## [important] Server-generated seq events (player.connected/disconnected) break the snapshot+replay contract
open()/close() emit player.connected/disconnected 'seq++' events, but these are not client actions and nothing says they are appended to the PersistQueue with fx. If they consume seq without a persisted row, rehydrate's replay produces a different final seq than clients hold (unique(gameId,seq) collisions on the next persisted action, spurious resyncs, snapshotSeq guard failures in the data model). Additionally, PlayerState.connected lives inside the snapshotted state, so after a restart the rehydrated state claims everyone is connected while zero peers exist. Fix: either move connection status out of the seq'd, persisted state entirely (broadcast it as a non-seq presence message, derive it server-side from room.peers), or persist connect/disconnect as first-class system events and reset all connected flags to false during rehydration.

## [important] GET /api/lobbies returns inviteCode for every open lobby — 'unlisted' privacy doesn't exist
Endpoint 14's response includes inviteCode for all OPEN lobbies, so the shareable link is public to every user of the instance and 'the invite link is the only discovery path for password-less private play' is false: any password-less lobby is joinable by anyone browsing the list. There is also no visibility/unlisted column on the Lobby model to support the claimed 'unlisted != passworded; both supported'. Fix: add Lobby.visibility (PUBLIC|UNLISTED), list only PUBLIC lobbies, and even for public lobbies return an opaque lobby id for the join call rather than the invite code (or accept that listed == open-to-all and make that explicit in the UI). Also add per-user/IP throttling on POST /api/lobbies/:code/join password attempts — scrypt at 50 ms does not stop an online brute force of weak lobby passwords.

## [important] No Origin validation on the WebSocket upgrade (CSWSH defense-in-depth missing)
WS auth is 'cookie rides the upgrade request' only. SameSite=Lax does block cookies on cross-site ws handshakes in current Chromium/Firefox, but the design leans entirely on that: the engine doc's client-side sketch even floats a non-httpOnly useCookie variant, and older/edge-case browser behavior around ws + SameSite has varied. A cross-site page opening wss://host/ws/game?g=... with an ambient cookie would get a fully authenticated game socket (read opponent-redacted state, act as the victim). Fix: in upgrade(), reject unless the Origin header exactly matches the configured public origin (and keep the cookie httpOnly, minted server-side only — delete the non-httpOnly variant from the client doc). Two lines, closes the class.

## [important] No input bounds or flood control anywhere: one message can OOM the room
Unbounded fields that land directly in state/events: token.create quantity (quantity: 1e6 creates a million CardInstances -> snapshot serialization OOMs the single process and poisons every future rehydrate), TokenSpec.name/text/typeLine lengths, game.roll sides/count (crypto.randomInt loop + giant results array), deck.mulligan draw, deck.draw n (bounded by library, good — the only one specified), player.life/counter deltas (1e308 floats survive JSON), card.counter negative overflow, x/y outside 0..1. Also absent: ws maxPayload (the node ws default is 100 MiB — a 90 MB JSON gets fully parsed before zod sees it), per-connection message rate limits (card.position from a hostile client at 1000/s each consuming seq + a persisted row; resync spam forcing 60–120 KB snapshot serialization per request; chat flood). Fix: zod .max() bounds on every numeric and string field (quantity <= 20, sides <= 1000, count <= 20, draw <= 20, text <= 300, name <= 100, life delta |x| <= 999, x/y clamped 0..1), crossws/ws maxPayload ~64 KB, and a small token-bucket per peer (e.g. 20 msgs/s burst 60, positions coalesced server-side to the latest per card per 100 ms, resync max 1/5 s).

## [important] Rehydration has no single-flight guard: concurrent reconnects create split-brain rooms
Lazy rehydrate is async (DB snapshot load + event tail replay). Two players reconnecting simultaneously after a restart/eviction both find rooms.get(gameId) undefined, both start rehydrating, and the second rooms.set() orphans the first Room — peers registered on the orphan receive no further events, and both rooms' PersistQueues insert rows with the same seq (unique-violation crashes or, worse, interleaved divergent histories). The related eviction race: the 10-min evictTimer can fire while a peer is mid-open() on that room, snapshotting and deleting a room that is about to get a peer. Fix: keep a Map<gameId, Promise<Room>> and always await the memoized promise (single-flight); have the evict timer re-check peers.size === 0 AND no in-flight open() at fire time, and clearTimeout on any new attach.

## [important] Persist-queue failure handling and superseded-peer close are unspecified (silent event-log gaps, wrong presence)
(1) If a write-behind INSERT fails (DB restart, transient error), the design says nothing: if the queue drops the row and keeps accepting actions, the DB tail has a permanent seq gap and the next rehydrate either throws mid-replay or silently reconstructs a state missing one action then applies later events on top — corrupted recovery that manifests only after a crash. Fix: on persist error, retry with backoff while pausing the room (reject new actions with a SERVER_PAUSED error); if retries exhaust, force a full-snapshot write attempt and mark the game degraded — never continue appending past a gap. (2) The single-session supersede (oldPeer.close(4000)) triggers close(oldPeer) AFTER the new peer registered; if close() marks players[p].connected = false unconditionally, the freshly reconnected player is broadcast as disconnected and (worse) counts toward the zero-peers eviction check. Fix: close() must only flip presence if no other live peer maps to that playerId, keyed strictly by peer.id.

## [important] card.position consumes seq and a DB row per drag tick — event-log and replay bloat
At the client throttle of ~10/s, a single 3-second drag emits ~30 seq-consuming, persisted events; a normal 3-hour 4-player game is plausibly 10–50k position rows dominating GameEvent, inflating every rehydrate replay and (under the data doc's model) triggering a full ~150 KB snapshot UPDATE per tick — hundreds of MB of WAL/TOAST churn per game. Fix: make card.position a non-seq ephemeral message (broadcast live, applied to in-memory state, NOT appended to GameEvent), and fold final positions into state so the next regular snapshot captures them; accept that positions may be up to one snapshot stale after crash recovery (cosmetic only). Alternatively coalesce: persist only the last position per card per action-pipeline flush. Also verify the 25-action snapshot counter isn't advanced by position spam (it would otherwise snapshot every 2.5 s during a drag).

## [nice-to-have] Dev HMR: unflushed write-behind tail + reducer edits replaying old events through new code
Every server/ file edit reloads Nitro: (a) the in-flight PersistQueue tail (up to ~1 s of actions) is lost on every save — during active playtesting this constantly rolls the table back a click or two; hook Nitro's close/beforeExit to flush the queue and write a final snapshot so dev reloads are lossless, unlike crashes. (b) After editing reducer.ts, rehydration replays the pre-edit event tail through the NEW reducer — if the edit changed semantics, the recovered state diverges from what players saw with no error. Mitigate in dev by forcing an immediate snapshot on reload (making the tail empty) and/or stamping events with a reducerVersion and refusing cross-version replay (snapshot-only recovery in that case).

## [nice-to-have] No client-side fallback when cards.scryfall.io is unreachable or an image 404s
300 hotlinked <img> tags is fine for rate limits (verified exempt), but a Scryfall outage or a rotated/retired image URL currently means a board of broken-image icons with no way to play. Fix for v1: an onerror handler swapping in a text placeholder rendered from name/manaCost/typeLine/pt (all already in the catalog row) so the game stays fully playable image-less; optionally a tiny Nitro proxy route with disk cache (~150–300 MB for small JPGs, sanctioned) behind a config flag — it also stops leaking every player's IP and per-card game activity to Scryfall.

## [nice-to-have] Import script edge cases: TRUNCATE lock, nameNorm unique collisions, card/alias atomicity
(1) TRUNCATE CardAlias takes ACCESS EXCLUSIVE — concurrent decklist imports on a live instance block or error during the weekly re-import; use DELETE FROM (MVCC-friendly) or build CardAlias_new and swap in a transaction. (2) Card.nameNorm is UNIQUE but the normalizer (NFKC + lowercase + diacritic strip + ae-folding) can in principle collide two distinct oracle names; a collision aborts an entire 1000-row upsert chunk mid-import, leaving the catalog half old/half new with stale aliases if the script dies before the alias rebuild. Detect collisions in JS before writing, log and keep the first, and wrap card-upserts + alias rebuild in one transaction so a failed import is invisible rather than partial. (3) The gen_ulid_or_cuid() SQL sketch doesn't exist in Postgres — generate cuids in JS and pass them in the unnest arrays.

## [nice-to-have] Username/chat hygiene and mid-game moderation are absent
POST /api/auth/claim specifies no username constraints: 10 KB names, zero-width characters, names crafted to spoof log lines ('Bob drew 7 cards'), or duplicate names impersonating a seated player all pass. Enforce length 1–24, strip control/zero-width chars, trim, and render usernames/chat strictly as DOM text nodes (never v-html) — state that explicitly as an invariant next to the redaction invariant. Separately: kick is OPEN-only and any seated player can fire turn.next/turn.setStep/player.marker, so a mid-game griefer can permanently skip phases and cannot be removed; consider host-kick during IN_GAME (seat becomes conceded) or a table-vote, and restrict turn.setStep to the active player + host as a default etiquette guard.
