## [blocker] The two design chains contradict each other on core architecture — must be reconciled before any code
The 'data' and 'engine' docs describe two incompatible systems. Persistence: data doc = one transaction per action writing the FULL snapshot with a snapshotSeq optimistic guard, events 'never replayed through game logic'; engine doc = write-behind event queue, snapshot every 25 actions/15s, crash recovery via deterministic fx-replay of the event tail. Schema: data doc has User/Lobby/LobbySeat/Game/GamePlayer/GameEvent(payload+publicLog); engine doc sketches Player/Game(hostId,passwordHash)/GameSeat(deck Json)/GameEvent(action+fx). API: /api/auth/claim + /api/lobbies/:code vs /api/session + /api/games/:id; WS path /api/games/:id/ws vs /ws/game?g=. Password hashing: scrypt vs bcrypt. Identity: GamePlayer(userId,seatIndex) vs 'PlayerId uuid minted at seat claim'. Fix: pick one persistence model explicitly (note: data doc's snapshot-per-action is fatal combined with engine's card.position drag stream — 100–200 KB jsonb × ~10 msg/s per dragging player; engine's fx-replay model handles this, so adopt it and drop the per-action snapshot), then merge the schema and API tables into a single source of truth and delete the loser.

## [blocker] The entire game-board UI/UX is unspecified — the product's whole reason to exist
The stated goal is 'more user-friendly than Cockatrice', yet neither doc contains a single line about the table screen: how 4 battlefields + 4 graveyard/exile/command zones + your hand + the stack + the log fit on one 1080p screen (Cockatrice's worst failure mode in 4-player is exactly this); card hover preview/zoom (which image size, where it renders, does it show back faces and oracle text); zone browser overlays (click a graveyard/exile to scroll it); drag-and-drop semantics (drop targets for zone changes vs free positioning, drop on library = top or bottom or a choice popover); multi-select (marquee/shift-click) feeding card.tap's cardIds[]; how counters render on cards and the quick-path for +1/+1 (typing a counter name in a dialog per click will get the app abandoned turn one); phase ribbon and active-player indication; whose-turn/priority nudges. Fix: a third design chain (wireframes + interaction spec) covering layout at 1080p and 1440p, hover-zoom, zone viewers, drag rules, multi-select, counter chips with one-click +1/+1, and the phase bar. Without it the two backend docs describe a protocol with no playable client.

## [blocker] Clients cannot render cards: no name/image in redacted state and no batch catalog endpoint
RedactedCard/ClientGameState carry only catalogId — no card name, no image URL, no type line. The only lookup is GET /api/cards/:id, one card per request: a 4-player sync references 300–450 instances → 300+ sequential fetches on every reconnect. Worse, the engine doc defines CatalogId as 'MTGJSON uuid' while the data doc's Card table never stores an MTGJSON uuid (PK is a cuid, natural key is scryfallOracleId) — the id spaces literally don't join. Fix: define catalogId = Card.id (cuid), embed {name, imageSmall, imageNormal, backImage*, typeLine} directly in visible RedactedCards (cheapest, keeps events self-contained), or add POST /api/cards/batch {ids[]} + client-side cache; also specify how tokens with fromCatalogId resolve their image.

## [important] No attack/blocker declaration or targeting arrows
The turn model has attackers/blockers/damage steps but no way to express 'this creature attacks Carol' or 'this blocks that'. In 4-player manual Commander this ambiguity occurs every single combat, and it's precisely why Cockatrice has drag-arrows (its most-used manual-play feature). Text chat ('the 3/3 attacks Bob... no, the other 3/3') is miserable. Fix: minimum viable = card.arrow {fromCardId, toCardId|toPlayerId, color} broadcast + auto-cleared on turn.next past combat, rendered as an overlay line; arrows double as spell-targeting indicators for the stack. This is ~1 event type + 1 canvas overlay and transforms combat usability.

## [important] Conceded/left players' boards are frozen and turn order doesn't skip them
game.concede flags the player and keeps them visible, but the authorization matrix says card actions require actor = controller/owner and moving cards out of an opponent's zone is denied — so after a concede (which happens in most 4-player games) nobody can remove the leaver's permanents, return stolen cards, or clean their side; the board rots for the rest of the game. Also unspecified: whether turn.next/turn.pass skip hasConceded players — if not, the game stalls every rotation on a player who left. Fix: on concede, either auto-remove all cards the player owns (MTG rule 800.4a — correct default) with control of other-owned cards they controlled reverting to owners, or open their cards' controller rights to the whole table; and make the reducer skip hasConceded (and long-disconnected?) players in turn rotation, with a log line.

## [important] Commander tax is a hand-rolled per-player counter, not per-commander
The only mention is player.counter 'commander-tax' — one free-form number per player. With partners/backgrounds (which the design supports) tax is tracked per commander, and the number players actually need at cast time is '2 + 2×tax'. Nothing increments it and nothing displays it near the command zone. Fix: taxByCommander: Record<CardId, number> on PlayerState, auto-increment (or one-click prompt) when a card with isCommander moves INTO the command zone from anywhere except game setup, render the current cast cost as a badge on the command-zone card, and allow manual adjust. This is a 10-line reducer addition that removes the single most common bookkeeping error at real tables.

## [important] Mulligan flow is not the London mulligan and has no pregame window
deck.mulligan {draw: number} (hand→library, shuffle, draw `draw`) is Vancouver-shaped; London = always draw 7, THEN put N on the bottom in chosen order. The doc's 'player bottoms manually via card.move afterwards' means 3 separate drag operations with no order control and easy misclicks into 'top'. Also missing: any pregame phase — the game starts at turn 1/untap with 7 drawn, so mulligans happen 'during' player 1's turn in the log and there's no per-player keep/mull confirmation gate; and no mulligan counter (free first mulligan is the universal EDH convention — the log should say 'mulligan #2, keeping 7, bottoming 1'). Fix: deck.mulligan {} always redraws 7 and bumps a per-player mullCount; keeping opens a peek-like 'choose N to bottom' overlay resolved via the existing peek.resolve toBottom shape; add a 'mulligans' game status between started and turn 1 with per-player keep flags.

## [important] Game log and chat vanish on every reconnect, refresh, and server restart
The log is derived client-side from the live event stream, and sync carries only ClientGameState — so a page refresh, a dropped socket, or the promised server-restart survival wipes every player's log and chat mid-game ('wait, how much damage did I take last turn?'). Post-hoc redaction of stored events is nontrivial in the engine doc's model (rows store raw action+fx; deciding what a viewer may see requires state at that seq), and the data doc's publicLog is public-only (loses your own private lines like 'you drew X'). Fix: persist, per event, the pre-rendered public log line plus optional per-seat private line (extend the data doc's publicLog to publicLog + privateLog[seat]), and include the last ~200 log entries (viewer-filtered) + chat tail in the sync payload.

## [important] Attachment lifecycle and stacking are unspecified
attachedTo: CardId with a server-side cycle check is all there is. Unspecified: what happens when the host leaves the battlefield (dangling attachedTo pointing into a graveyard/hand — does the reducer auto-unattach, and is that a logged event?); what happens to attachments when their host is a token that gets deleted; whether attached cards' x/y follow the host during drag or are recomputed; and visual stacking (offset direction, z-order, and the order of multiple auras/equipment on one creature — players use physical stacking order to remember things). Fix: reducer rule 'host leaves battlefield ⇒ all attachments auto-unattach in place, logged'; attachments render offset-stacked under the host in attach order, move with the host, and attach order is an explicit array (or ordinal) so it survives serialization.

## [nice-to-have] Day/night and generic shared table markers missing
markers is hardcoded to {monarch, initiative}. Day/night (MID/VOW), the dungeon room a player is in (initiative without a dungeon display is half a feature), and storm-ish shared counters have no home; per-player player.counter is the wrong scope. Fix: generalize to a table-level markers: Record<string, string|PlayerId|null> plus a day/night toggle in the UI; dungeon display can stay a v2 image overlay.

## [nice-to-have] Reveal granularity gaps: whole-hand-to-one-player, top-of-library-to-others, opponent searches your library
card.reveal {to: PlayerId[]} covers single cards, but 'reveal your hand to one player' (common political/effect play) requires N separate actions, deck.revealTop is all-public only, and effects where an opponent looks at or searches YOUR library (Praetor's Grasp, Bribery — Commander staples) are unrepresentable since peeks only target your own library. Workarounds exist (reveal one-by-one, temporary trust), so deferral is acceptable, but add hand.reveal {to} and a grant-peek-on-my-library action to the v2 list explicitly.

## [nice-to-have] Stack copies and mid-peek library mutation are undefined reducer edges
token.create has no zone parameter (implicitly battlefield), so spell copies on the stack (Fork effects, casting from a peek while a scry is open) can't be represented — and 'tokens are DELETED when they leave the battlefield' would eat a stack copy anyway. Separately, Peek holds cardIds by reference: if the library mutates during an open peek (you draw for a triggered ability mid-scry, or another effect shuffles), the peek is stale and peek.resolve's semantics are undefined. Fix: allow token.create {zone: 'stack'|'battlefield'} and change the deletion rule to 'deleted when leaving stack/battlefield to anywhere else'; make library-mutating actions by the peek owner either rejected or auto-cancel the peek.

## [nice-to-have] No server-side rate limiting on actions or chat
card.position throttling is client-side only ('throttled client-side to ~1/100ms'); a buggy or hostile client can stream thousands of position/chat messages, each consuming a seq, a broadcast to 4 peers, and a persisted event row. Single-node with 4 trusted players makes this low risk, but the invite link is shareable. Fix: cheap token-bucket per peer in the ws message handler (e.g. 20 actions/s burst 40, positions coalesced server-side to last-write-wins per 100ms per card, chat 2/s) — a dozen lines that also caps the replay-tail bloat.
